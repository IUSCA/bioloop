# e2e — browser tests for the v2 groups system

Separate from `tests/`, which covers v1 and is organised around the RBAC roles `admin`,
`operator`, and `user`. v2 has no roles below platform admin — what a person may do follows
from group standing and grants — so the two suites need different fixtures and different
configuration. **Do not add v2 specs to `tests/`, and do not edit it.**

- What the suite must prove: [docs/design/groups/e2e-test-flows.md](../docs/design/groups/e2e-test-flows.md)
- How it gets built: [docs/design/groups/implementation/e2e-test-plan.md](../docs/design/groups/implementation/e2e-test-plan.md)

## State

Phase 0 only. The single spec here answers spike 1 and is throwaway; there is no world
builder, no persona fixture, and no page-object layer yet.

## Running it

```bash
docker compose up -d postgres redis mailhog
bin/devserver.sh up
cd e2e && npm install --ignore-scripts && npx playwright test
```

`--ignore-scripts` skips Playwright's browser download. The config uses `channel: 'chrome'`,
so it drives the Chrome already installed on the machine. A run on a host without Chrome
needs `npx playwright install chromium` and the `channel` line removed.

The API must be up before the suite starts. `bin/devserver.sh status` reads a pidfile holding
the **nodemon** process, which outlives a crash of the app it supervises, so it reports
`running` over a dead API. Probe the ports instead — and note that a **401 from the API means
it is alive** and demanding authentication:

```bash
curl -sk -o /dev/null -w "%{http_code}\n" https://localhost/       # expect 200
curl -s  -o /dev/null -w "%{http_code}\n" http://localhost:3030/   # expect 401
```

## Signing in

Specs authenticate through `/dev-login?username=<user>&next=<path>`, which calls
`POST /auth/test_login` — no credential, and registered only in a recognised development
mode (`localhost`, `docker`, `ci`).

**Never drive a spec as `test_user`.** The authorization engine allows a platform admin
before any policy runs, so a pass driven as one exercises no policy path at all. Use a group
admin. Which seeded account administers which group is generated by a hash and moves whenever
the seed changes, so the eventual suite builds its own groups and assigns standing to
borrowed accounts rather than hard-coding names.

## After a database reset

`prisma migrate reset` re-seeds with new `subject_id` values, and the API validates access
types at startup — it exits while the table is briefly empty and nodemon does not retry.
Restart the API afterwards. A token minted before the reset authenticates fine and then dies
inside a write on a foreign key, surfacing as a 409 about a constraint violation.
